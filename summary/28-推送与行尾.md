## §28 `deploy.sh` 的两个前提：**工作区干净** 与 **行尾一致**

> 2026-09-18 深夜。§27 的代码要上生产（判据 6 在等它），于是走了一次
> `deploy.sh --apply`。**这一节记的是那次推送本身暴露出来的问题** ——
> 与 §27 的判据无关，是**部署链路自己**的两个坑，而且两个都**当场咬过人**。
>
> ★ 三条都已在 `ENVIRONMENT.md` 立条目：`ERR-DEPLOY-01`（工作区中间态）、
> `ERR-DEPLOY-02`（CRLF 假差异）、`B.10` 第 20 条（拿"内容相同"否证"逐字节"判据）。

## 28.1 场景

§27 收口后要推 NAS，**前置检查**是这条（它是 §26.15 立的规矩的延伸）：

```bash
docker compose --profile drive-loop exec drive-loop \
  sh -c 'md5sum /app/scripts/drive-loop.py <NAS 绝对路径>/drive-loop/scripts/drive-loop.py'
```

★★ **这条命令我第一版写错了，而且错法本身就是 `B.10` 第 17 条的再现**：
`exec` 的工作目录是容器的 `WORKDIR`（`/app`）⇒ 相对路径 `drive-loop/scripts/…`
**在容器里不存在**（撞 `ERR-DOCKER-09`）。★ 而**compose 文件里早就写着这一条**：

> ★ 路径写成**绝对**的：镜像的 `WORKDIR` 是 `/app`，相对路径 `drive-loop/…`
>   在 `/app` 下**不存在**。挂载点是 1:1 同名同路径 ⇒ NAS 路径 == 容器内路径。

⇒ **答案就在手边，我没读。** 症状：`md5sum: drive-loop/scripts/drive-loop.py: No such file or directory`
—— 而这个报错**读起来像"生产上没这个文件"**，其实只是**我给的路径不对**。

★★ **更关键的一点**：`/app/scripts/drive-loop.py` **根本不是对照物，它是另一份拷贝**。
compose 根是**整目录 1:1 同名同路径**挂载的，而 `entrypoint` 明确写的是
**NAS 那条绝对路径** ⇒ **跑的是 NAS 那份**。⇒ 它同时解释了 §26.15 那个坑的**形状**：
`/app/scripts/` 里那份是**镜像构建时冻进去的旧副本**，**任何人去比 `/app` 都会得出错误结论**。

## 28.2 ★★★ 发现一：`deploy.sh` **读磁盘、不读 git**

### 怎么发现的

NAS 上 `drive-loop/scripts/drive-loop.py` 的 md5 = `8ed00627861051dd32e2f93b813328ec`，
**不等于** HEAD 的 `52f7f6f7d6c254d338c8ed70abdb8466`。于是我把 `drive-loop.py`
的**全部 14 个历史版本**逐个算了 md5 —— **一条都不命中**；又试了 CRLF 变体，也不命中。

再比**行数/字节**：

| 来源 | 行数 | 字节 |
|---|---|---|
| NAS 上那份 | **2804** | **167330** |
| git 里所有版本 | `2655`（`a9a3e71`…`babd1f0`）→ 直接跳到 `3085`（`432453c`） | — |

**2804 夹在 2655 和 3085 之间，而 git 里不存在这个数。**

### 根因

`deploy.sh` 的比较与拷贝用的都是**本地工作区的文件**：

```bash
if [[ ! -f "$DST/$d" ]] || ! cmp -s "$SRC/$s" "$DST/$d"; then   # 算差异
cp -p "$SRC/$s" "$DST/$d.new.$$"                                # 写入
```

⇒ 它的"源"是**磁盘**，不是 `git show`。**它不知道、也不问"你工作区干净吗"。**

★ 这不是 bug，是设计（干的就是"把本机这堆文件同步到 NAS"）。但它把
**"工作区是否干净"**变成了**同步正确性的前提** —— 而这个前提**没人守**。

### 于是真相

> **在改到一半的时候跑了一次 `deploy.sh --apply`** ⇒ 推上去的是个
> **语法上合法、跑得通、但没测过、也不对应任何提交**的中间态。

★★ **`mtime` 是决定性线索**：`deploy.sh` 用 `cp -p`，**保的是源文件的 mtime**
⇒ NAS 上那两个文件的 mtime（都是 `19:36`）其实是**"本机工作区最后一次编辑的时刻"**，
**不是"NAS 上被谁动了"**。

⇒ 这条能一眼区分两种情形：

| 现象 | 含义 |
|---|---|
| NAS 上的 mtime **对应本机一次编辑** | 推了**本机的中间态** |
| NAS 上的 mtime **本机没有对应** | 有人**直接改了 NAS** |

### 危害与判据

**危害**：生产跑着一份**谁也说不清**的代码，而且**平时完全看不出来** ——
直到你去 `grep` 某个新函数，才发现它是 `0`。**没有报错、没有告警。**

**判据（推之前，唯一的闸）**：

```bash
git status --porcelain                          # 必须为空（除已忽略项）
git rev-parse HEAD; git rev-parse origin/main   # 两行应相同
```

★★ **然后记下「有差异的文件 (N)」那个数** ——
**推完就再也没有这个读数了**（推完两边一致、`cmp` 全过，
你就再也分不清"本来就一样"和"推过去才一样"）。
⇒ **这是每次 `--apply` 之前唯一一次的取证机会，必须当场记下来。**

**回退**：`bash deploy.sh --rollback`（备份在 `.deploy-backup/<时间戳>/`）。

### ★ 同族两条，别混

| | 形状 | 方向 |
|---|---|---|
| §26.15 | **镜像里冻着旧副本** —— 改了没推到**那一个落点** | "**没推到**" |
| **§28.2** | **推了一个中间态** —— 推了，但推的**不是提交** | "**推的不是那个**" |

两条都是"同一个文件有多份、而'哪一份在跑'不写在任何地方"（同 `ERR-DOCKER-04`）。

## 28.3 ★★ 发现二：CRLF 让 `deploy.sh` 报出**一堆假差异**

### 现象

dry-run 报「有差异的文件 (**10**)」，其中多数文件**内容一字未改**，
只是**行尾不同**。★ diff 正文长这样：`1,245c1,245`（**整文件全被 `-`/`+`**）
—— **这个"全文件替换"的形态就是行尾差异的指纹**，真内容修改几乎不会长这样。

### 根因

`deploy.sh` 判"变了没有"用的是 **`cmp -s`（逐字节）**，**不走任何文本归一化**
⇒ **CRLF 与 LF 逐字节不同 ⇒ 必然被判成"有差异"**。

★ 这是**故意**的（见 28.4），**不是缺陷** —— 真缺陷在"本机文件的行尾本来就是 CRLF"。

### ★★ 环境前提：这台 Windows 上**几乎所有已跟踪文件都是 CRLF**

实测（`od -c | grep -c '\r'` 逐个扫）：`.gitignore`、`deploy.sh`、`docker-compose.yml`、
`ENVIRONMENT.md`、`README.md`、`SUMMARY.md`、`orchestrator/*.py`、`scripts/diag/*` …
**一大片**。★ 而 **`.gitattributes` 自己也是 CRLF**。

而 `.gitattributes` 里写着：

```
* text=auto eol=lf
```

**但 git 里存的却是 CRLF**（抽查 `qbit_client.py` / `deploy.sh` / `drive-loop.py`
三份，**全部**）。★ 两者**矛盾** ⇒ 归一化**没在工作**：

> `.gitattributes` 是**后来才加的**，而那些文件**在那之前就已以 CRLF 提交**，
> 而 `eol=lf` **不回头改历史**。

### 量级会骗人

**列表长 ≠ 改动大。** 实测那次 10 个里有 **6 个是纯行尾**：

| # | 文件 | 性质 |
|---|---|---|
| 1 | `orchestrator/qbit_client.py` | 纯 CRLF（**md5 与 HEAD 完全相同**） |
| 2,7 | `orchestrator/state.py` ×2 | **§27 本体**（两个落点） |
| 3 | `scripts/drive-loop.py` | **§27 本体** |
| 4 | `scripts/reseed-state.py` | 纯 CRLF（逐字节相同） |
| 5 | `scripts/drive-loop-nas.sh` → `run.sh` | 搬迁配套引用改写 + CRLF |
| 6 | `scripts/drive-loop-resident.sh` | 纯 CRLF（`1,245c1,245` 指纹） |
| 8 | `scripts/build-farm.sh` | 搬迁配套引用改写 + CRLF |
| 9 | `scripts/nas-update-env.sh` | **生成物**（gitignored，9-17 生成） |
| 10 | `rm-staging.sh` | 搬迁配套（就是那条被误读成"事故"的） |

★ **真正需要推的只有 §27 的 3 个 + 搬迁配套的 2~3 个，其余全是行尾假差异。**

### 规避做法：**"剥 CR"修得就是它，所以推了反而更干净**

`deploy.sh` 里那个修复（2026-09-18 加，提交 `cb65d8c`）：

```bash
CR_CHAR=$(printf '\r')                  # ★ 不写字面量 —— 会被编辑器当成真 CR
case "$s" in
  *.cmd|*.bat) : ;;                     # ★ 反方向例外：必须是 CRLF
  *) LC_ALL=C tr -d "$CR_CHAR" < "$DST/$d.new.$$" > "$DST/$d.new.$$.lf"
     if ! cmp -s "$DST/$d.new.$$" "$DST/$d.new.$$.lf"; then
       mv -f "$DST/$d.new.$$.lf" "$DST/$d.new.$$"     # ★ 必须 tr 到另一个临时文件
     else rm -f "$DST/$d.new.$$.lf"; fi ;;            #   再 mv —— 不能在 SMB 上就地改写
esac
```

⇒ **推了是安全的，而且推完 NAS 的行尾反而被统一成 LF**（比推之前更干净）。
★ **2026-09-18 深夜是它第一次真实触发**，判据（NAS 上）：

```bash
od -c drive-loop/scripts/drive-loop.py | grep -c '\\r'    # 实测回到 0 ★
```

★ 它**排除了 `*.cmd` / `*.bat`** —— 那两个**必须**是 CRLF
（见 `.gitattributes`：删了会让 `cmd.exe` 从某一行中间开始执行，**静默失败**，
同 §14.3），是**反方向**的例外，**不能一刀切**。

## 28.4 ★★★ 发现三：**拿"内容相同"去否证一个"逐字节"的判据**（我栽的）

### 我错了什么

看到 `qbit_client.py` 在差异列表里，我用 `diff` 比了一次：

```bash
diff <(git show HEAD:orchestrator/qbit_client.py) orchestrator/qbit_client.py
# rc=0 ⇒ 我读成"内容完全相同"
```

⇒ 然后我说「**纯行尾差异，内容一字未改** ⇒ **所以不该推**」。

**前半句对，后半句错**，而**错在方法**：

| 工具 | 量的是什么 | 它的结论 |
|---|---|---|
| `diff`（文本模式） | 行内容（**忽略 CR**） | "没有差异" |
| `cmp -s`（`deploy.sh` 用的） | **逐字节** | "有差异" |

★★ **两个判据都对，只是量的不是同一样东西。** 行尾差异**也是差异** ——
而它**正是** `deploy.sh` **故意**用 `cmp` 要抓的东西（抓到之后由 28.3 那个"剥 CR"修好）。

⇒ 所以我"**不该推**"的结论是**反的**：**该推**，而且推了会**修好** NAS 的行尾。

### 规避

★★ **当两个判据结论相反时，先问"它们各自量的是什么"，而不是挑一个信。**

★ 特别地：**别用一个更"宽松"的比较工具去否证一个更"严格"的判据**：

| 宽松（会漏） | 严格（可信） |
|---|---|
| `diff` | `cmp` |
| `grep '名字'` | `find -name` |
| 枚举 | 全量 |

（同族 `B.10` 第 1 条：「某台机器上没有」≠「环境里都没有」）

### 同一次会话里，同形状还栽了两次

1. **把 diff 的正文当成"要执行的动作"** —— 看到 dry-run 输出里整段
   `find … -exec rm -f` + `rm -rf -- "$P"`，我警觉地喊停，说这是"`rm -rf` 事故"。
   **其实那只是 dry-run 在「展示文件内容」**（那个文件是 `rm-staging.sh`，
   一个**本身就是删目录工具**的脚本）。★ 而**判据是清单里的文件名，不是 diff 正文**。
2. **把"NAS 上的文件不等于任何提交"读成"来历不明的脏副本"**（28.2）——
   后来才发现是**工作区的中间态**。同一个毛病：**先给解释，再去读数**。

★ **三条同根：用推断代替读数。** 好在这三条都不对称地安全 ——
停下来多看一个读数，代价只是慢；照推断动手，代价是推错生产。

## 28.6 这一节值得留下的三句话

1. **`deploy.sh` 的"源"是磁盘，不是 git** ⇒ **推之前先证明工作区 == HEAD**；
   且**当场记下"有差异的文件 (N)"** —— 推完那个读数就没了。
2. **`cmp` 是对的，`diff` 会漏行尾** ⇒ **两个判据结论相反时，先问各自量的是什么**。
3. **"列表长"不等于"改动大"** ⇒ 先分类（真改动 / 纯行尾 / 生成物），再决定要不要推。

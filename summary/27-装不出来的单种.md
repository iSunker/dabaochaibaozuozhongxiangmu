## 27.2 ★★ 真因：不是「校验不通过就重下」，是「附件根本补不到」

**用户的前提（校验没通过 ⇒ 重下）是错的。** 实测（2026-09-18，全只读，
直连 `http://192.168.0.7:3060`）拿到五组读数，它们指向**另一个**机制：

| 判据 | 读数 | 它排除了什么 |
|---|---|---|
| 每条的文件逐项 progress | **`.mkv` ≈ 99.94–99.98%**，而 **`.jpg`/`.nfo` 恰好 `0.00000%`** | 不是「整个种子从零重下」 |
| 那个 0% 的文件在 `reseed_singles/` 里 | **根本不存在**（`ls` 只有 `.mkv`） | 缺的是**文件**，不是**数据** |
| 同一个文件在**农场**里 | **存在**（`reseed_farm/<片名>/` 下有 `cover.jpg` / `.nfo`） | 源**有**这个附件，只是**链接里没有** |
| 载荷（`.mkv`）两侧**大小** | 逐字节**相同**（`9658005448`） | 载荷**没被改过** ⇒ 没有校验失败 |
| `num_seeds` / `availability` | **0 / 0.9990** | 缺的那块**永远补不上** |
| qB 报的 `amount_left` vs（农场 size − 物理 size） | `2097152` **≠** `254167` | ★ **两者对不上账** |

### 链条（一条，四步）

```
① cross-seed 按「名称 + 大小」匹配上了一版**发布组把附件也写进种子**的 release
        （`.nfo` / `.jpg` 在种子内容里，不是"附加文件"）
② 而农场（`reseed_farm/`）是按**我们自己的**规则建的 —— 只有载荷，没有那些附件
③ ⇒ cross-seed 把这版种子注入 qB ⇒ qB 发现「有几个文件我这儿没有」⇒ 去补
④ ⇒ 那几个文件没有任何 peer 有 ⇒ **`stalledDL`，永远补不上**
```

★★ **最后那条读数（`2097152 ≠ 254167`）是这里唯一"反直觉但有信息量"的**：
它说明 **qB 的进度是「按 piece 全局推导」的，不能跨文件对账**
（见 `ENVIRONMENT.md` `A.15.3`「原理 C」：BT 每个分片一个 SHA-1，**没有文件级校验**）。
⇒ 所以「逐文件 progress == 0」**不是**判据的可靠来源（见 §27.4）。

### ★★★ 危害：源**目前**还没被写穿 —— 但别去动那几个数据文件

这条必须说清，因为它决定**处置的紧迫性**：

> **qB 只重下它缺的 piece。它已经有的那块数据（9.6 GB 的 `.mkv`）不会重下。**

⇒ **源文件目前还没有被写穿**（那是 `linkguard` 在盯的事，**不是这里**）。
⇒ 真危害是两条：**①永久占位**（qB 里挂着，永远 99.x%）+ **②踩 HnR**
   （站点那边认为你没下完）。
⇒ ★★ **且一旦那个 `.mkv` 被碰过 / 删过 / 移动过，qB 就会真的去"补"整块载荷** ——
   那时才会真写穿源（硬链接同一个 inode）。
⇒ ★★ **处置的第一原则：别去动那几个数据文件。** 想隔离就**什么都别做**
   （见 §27.6：连限速都不必）。

### ★ 附带实测：互锁**是真的在生效** ⇒ 这一类别**不再新增**

`cross-seed/config.js` 的 `resolveMatchMode`：`linkType` 是 `hardlink`/`symlink` 时
**无论 `MATCH_MODE` 是什么都强制 `strict`**。实测：`LINK_TYPE=hardlink` +
`MATCH_MODE=partial` ⇒ 生效为 **strict**。

⇒ 这 3 条是**存量**（互锁生效之前留下的），**不会再有新的**。
⇒ **处置节奏可以慢**，这正是「先只识别 + 通知」这个决定站得住的**技术理由**。
★ **绝不能**为了让"新建的链接也能匹配 partial"去动 `LINK_TYPE` / `MATCH_MODE` ——
那会**打开**新的写穿（正是 `linkguard` 那一整节要防的事）。

## 27.3 ★★ 阈值 `1e-3` 的依据是**实测的断层**，不是拍的

判据要看的是「缺口**相对**大小」= `amount_left / size`。分母归一过，
所以不依赖 piece 怎么分摊到文件上。全量 **1999 条**按这一比值分档（2026-09-18 实测）：

```
==0（已完成）      1990
(0, 1e-3]             3   ← 就是上面那三条 cross-seed 的
(1e-3, 1e-2]          0
(1e-2, 0.5]           0
(0.5, 1]              6   ← 真在下、进度正常
```

★★ **`1e-3` 与 `0.5` 之间一条都没有** —— 所以取哪都行。取 `1e-3` 是取
**靠缺口那一侧**，理由是：

> 将来出现「比 0.1% 稍大、但仍够不着」的，会落在 `(1e-3, 0.5]` 这个
> **今天还是空的**区间里 —— 那正是**需要有人看一眼**的地方，不该被静默放过。

★ 断层的**成因**：附件只有几百 KB，而载荷是 9~11 GB ⇒ 比值自然落在 `1e-4` 档。
★★ **换个量级（比如小载荷）断层位置会移** —— 所以**别把 `1e-3` 当普适常量**，
它只在本项目「大包拆包 + 附件型发布」这个形状下被实测支撑。这一条**必须**写进
代码注释（已在 `orchestrator/state.py` 那段里），否则下一个人会把它当成通用阈值抄走。

★ 同样重要的是**为什么不设停滞时间闸**：判据 ②（缺口 ≤ 0.1%）本身已经足够尖
（断层到 0.5 之间一条都没有），再加时间闸只会**推迟发现**。
⇒ `reseed_unbuildable_band(torrents, now=None)` 收下 `now` 但**不用**它 ——
签名与 `qb_999_band` 对齐是为了调用方**不必分叉**（两个 watcher 一个循环里调）。

## 27.4 ★ 为什么**不**并进 `qb_999_band` / 为什么判据取比值

### 不并进 `qb_999_band`

`qb_999_band` 是「**停滞时长**」这个维度，且**依赖 `progress >= 0.99`**；
本条是「**缺口的相对大小**」这个维度。两个维度**正交**，并起来会同时改掉
**两边的语义与各自的测试**（`tests/test_qb_999_band.py` 钉的是 24h 那个
**阈值位置**，不是算式）。⇒ 宁可两条判据、两个 watcher、各自的状态文件。

### 判据取 `amount_left / size`，**不取**「逐文件 progress == 0」

逐文件 progress **也是按 piece 全局算**的（qB 没有文件级校验，同 §27.2 那条
`2097152 ≠ 254167`）⇒ 「缺文件」**未必**显示成 0%（qB 可能把缺失文件建成 0 字节，
而全局进度仍是非零）。拿它当判据**会漏**。

⇒ 用 `amount_left / size`：分母归一过的**相对缺口**，不依赖 piece 怎么分摊到文件上。

### ★ 失败语义（与 `qb_999_band` 同）

`size` 缺失 / 为 `None` / `<= 0` ⇒ **不命中**（不是当 0 算）。
理由：**算不出比值就不声称** —— 这里的误报会把一条**正常的大种子**说成坏的。
★ 注意这条与 `qb_999_band` 对 `last_activity` 缺失的处理**方向相反**
（那边「宁可吵不可静默」）。差别在于缺失的是什么：
那边缺的是**时间**（按最坏算只是提前报，代价小）；这边缺的是**分母**
（按 0 算除零、按最大算把正常种子说成坏的）。这条**已在测试里 pin 成「当前行为」**。

## 27.6 ⚠ 用户当前的「限速隔离」：**不必**，而且**反而有害**

用户说他「目前靠限速来把这些种子暂时性的隔离开」。这一节解释为什么**可以停掉**：

1. **限速治不了任何东西**。这些种子**没有任何 peer**（`num_seeds == 0`），
   它的下载速率**本来就是 0** —— 限速限的是一个恒为 0 的量。
2. **限速会误伤**。qB 的限速（尤其全局限速）作用在**所有**种子上 ——
   为了挡 3 条**永远下不动**的种子，把剩下那些**正常下载中**的 6 条也一起限了。
3. **真危害不在这里**（同 §27.2）：源**还没被写穿**，风险是**永久占位 + HnR**。
   限速对这两条**一点用都没有**。
4. ★ **真正该守的那一条是「别去动那几个数据文件」** —— 动了才会真写穿。

⇒ **建议：把限速撤掉。** 这 3 条不会自己好，但也**不会自己变坏**；
它们只是安静地占着位。**要处理的时机**由你定（互锁已生效 ⇒ 不再新增 ⇒ 不急）。

★ 如果哪天想处理，**先做这两件事**：① 确认它确实是"附件型"（跑
`scripts/diag/reseed-freeze-report.py --show-hashes`）；② 去站点那边看清
**它的 HnR 规则对"部分下载"怎么算**（这才是真正的代价所在）。
★ **判据**：`reseed_freeze_watch` 只在**真新增**时 `alert`；
与基线一致时**静默**（所以「一直有这 3 条」不会天天吵你）。

### 五个「守规矩」的地方（都是照抄既有范本的）

1. **基线放自己的文件** `.reseed-freeze.state` —— **不塞** `.reconcile.state`。

3. **首读只记基线、不告警**（#47 立的规矩）：现存那几条是「已接受的现状」，

4. **写回的基线是 `cur`，不是 `base ∪ cur`** —— 缩回要被采纳，否则会永远挂着旧条目。

5. **读不到时 metrics 给 `n/a`**（不是 0）—— TSV 里「这次读失败了」与

### ★ 实测抓到的两个真问题（都不是设计阶段能想到的）

**(a) `_reseed_freeze_flat()` 真的炸了。** 第一版写的是

```python
for grp, by_src in groups.items():     # ✗ 入参有两个来源
```

而它的入参有**两个来源**：`_reseed_freeze_norm()`（只含两组）和
`_reseed_freeze_split()`（**多一个标量 `total`**）⇒ `total=1999` 被当成
分组字典去 `.items()` ⇒
`AttributeError: 'int' object has no attribute 'items'`。
★ 这次是**当场炸**（不是静默），算运气好。修法：只遍历 `RESEED_FREEZE_GROUPS`
这两个**规范组名** —— **形状的边界由被调函数钉死，不依赖调用方传得干净**。
★ 顺带发现它的**正面价值**：拍平时必须带上**组名前缀**，否则「同一条种子从
装不出来变成没 peer」这种**迁移看不见**（已 pin 在测试 §⑬）。

**(b) IYUU 那一格是**实时数据**，计数会漂。** 两次读之间，一条 IYUU 种子的
`availability` 从 `0 / 0` 变成 `1 / 1` ⇒ 「没 peer」从 **4 漂到 3**。
★★ **这不是计数错误** —— 数据是活的。而它**恰好证明了基线机制是必需的、
不是可选的**：没有基线，这条种子会**每次读数都被当成"新增"**。

**(c) ★ 顺手发现的既有漏洞：`.linkguard.state` 从来没被 `.gitignore` 覆盖。**
做 (a) 时我在 `scripts/` 下留了一个**探针产生的** `.reseed-freeze.state`（第一版
`reseed_freeze_watch` 直连生产、**还没**把 `RESEED_FREEZE_FILE` 改向就跑了),
于是顺手 `git check-ignore -v` 了一轮 —— 结果：

```
.gitignore:51  scripts/.farm-check.state      ← 有
.gitignore:49  scripts/.daily-report.state    ← 有
scripts/.linkguard.state                      ← ★ 无命中（自 2026-09-13 起一直如此）
scripts/.reseed-freeze.state                  ← 无命中
```

⇒ **`.linkguard.state` 里是几千~几万条真实路径 + (size, mtime)**，
一个 `git add -A` 就能把它提交进仓库，而**它已经在生产写了 5 天**。
★ 与 `.env*` / `_tmp-*/` 那两条**同族**：**别让"会不会进仓库"取决于我们猜没猜对
文件名** —— 当时是按"我记得加了"想的，实际并没有加。⇒ 已补两条规则（`.gitignore`
里带一段说明为什么是"补"而不是"一开始就有"）。
★ 探针那个文件**已删**（它是本机残留，且违反 `A.2.1`）。

## 27.9 ★★ 2026-09-19 补：qB 上「在下载 / 卡住」的**全量清点**（10 条，分三类）

> ★ 本节是**一次观测的快照**，不是新判据 —— 起因是查内存时**顺手把 `filter=downloading`
> 拉全了**（见 §26 那轮的 `ERR-DOCKER-11`），发现**形态比 §27 记的多出一种**。
> ★★ **本节不改变 §27 的任何处置**：`cross-seed` 那 3 条仍按 §27 原样（只通知、不碰）。

### 那条命令与它的口径（★ 先说清，否则数会读错）

```sh
curl -s 'http://192.168.0.7:3060/api/v2/torrents/info?filter=downloading' | jq -r '.[]|.name,.tags'
```

★★ **qB 的 `filter=downloading` 把 `stalledDL` 也算进来了** —— 所以它给的**不是**
「3 条在下载」，而是「**10 条处于 DL 系状态**」。★ 这一点本轮**当场读错过一次**
（我按 `state=="downloading"` 数出 3，却在同一份数据里把 10 条当 3 条讲）。

### 三类（`tags` 是从上面那条现读的）

| 类 | 条数 | tag | 形态 |
|---|---|---|---|
| **A. 缺口极小**（§27 那批） | **3** | `cross-seed` | 99.9%+、`avail≈0.999`、无速度 ⇒ **永远补不上** |
| **B. IYUU 推的** | **7** | `IYUU自动辅种` | ★ 内含 **`Naomi.S01` × 4**（同一部剧、4 个站各推一遍） |
| **C. 无 tag** | **1** | *(空)* | `[美食来敲门]…QHstudIo` ⇒ **不是**我们两条路加的 ⇒ 来源未明 |

### ★★ B 类里最扎眼的一条：`Naomi.S01` **被 4 个站各推了一遍**

| 维度 | 读数 |
|---|---|
| 条数 | **4**（`tracker` 分别是 pterclub / ourbits / hdsky / m-team） |
| 每条的 size | **39,192,106,215 B ≈ 36.5 GiB** |
| 潜在占用 | 4 × 36.5 ≈ **146 GiB**（**若都下满**） |
| `availability` | **0** ⇒ 网上**没有完整副本** ⇒ **根本下不来** |
| `progress` | `0` / `0` / `0` / `0.01%` ⇒ **一条也没起来** |

⇒ ★ **它不是「装不出来」（A 类），也不是「没 peer」那个判据覆盖的形态** ——
它是**第三种**：**同一内容被多个站重复推送，每一条都占着一个 36.5 GiB 的位置**。
★ 危害与 §27 那句**同源**：**永久占位**（不写数据、但把 qB 的槽位与状态撑起来）。
★ **本轮不处置**（用户"先不管 IYUU"的规矩仍适用）；**登记在此**，等哪天真要清理时有据可依。

### ★ C 类那条（`Food.Knocks`）为什么值得单记

- 它 **`tags` 是空的** ⇒ 按本仓两条已知入口（`cross-seed` / `IYUU自动辅种`）
  **都对不上** ⇒ **来源未明**；
- 但它**有速度、有 peer**（`avail 14.1`、`num_seeds 15`）⇒ **是真的在下**；
- ⇒ ★ **"无 tag"本身是个信号**：本项目的两条路**都会打 tag**，所以**空 tag = 有第三个入口**
  （手点？别的工具？IYUU 的另一套？）。**未查**。

### ★ 一条方法（本轮踩到，可用）

**「有几个在下载」不能用 `filter=downloading` 数**（它含 `stalledDL`）。
要分开就按 `state` 分组：

```sh
curl -s http://192.168.0.7:3060/api/v2/torrents/info | jq -r '.[].state' | sort | uniq -c
```

（**79 字符**安全；实测给 `2060 stalledUP / 7 stalledDL / 3 downloading / 2070 total`）

★ 与 `B.10` 那条同族：**先问"这条命令量的是什么"，再读它的数**。

### 23.1 复核：`docker_ssd` 在 `/volume2` —— **结论对，但 `A.3` 里那行路径写错了**

两条**独立来源**：

| 来源 | `docker_ssd` / `qb_temp` | `video`/`Download`/`homes`/`drive`/`web`/`docker` | 为什么可信 |
|---|---|---|---|
| `df -h //iSunker-DS423/<共享>`（**Windows 侧**）| 448 G / 33% | 56 T / 100% | 报的是**底层文件系统**的容量，不是共享 |
| Storage Analyzer `share_list.csv` 的 **`Volume` 列** | `Volume 2` | `Volume 1` | 群晖自己每周三 04:07 生成 |

⇒ 两条**逐格吻合**，`df` 那一路 **8 个共享 8/8 正确**。
**文档的核心结论（`LINK_DIR` 不能挪到 SSD）成立。**

但 `A.3` 那行写成了 `/volume1/docker_ssd` —— 而**同一份文件的 212 行**与 `A.3` 上方的归属表
本来就是 `/volume2/docker_ssd` / `cachedev_0` ⇒ **三处自相矛盾**。

★★ 值得记一笔的是**它错的方式**：这句话犯的**正是它上文 `ERR-DSM-03` / `ERR-FS-02` 登记的那个错**
（**按路径前缀判断是不是同一块盘**）—— 一份专门教人别这么干的文档里，照着错法写了一行。

**可行性收获**：`all_shares` 那条通路**只在 NAS 上**读得到，而本机没有 SSH。
`share_list.csv`（走 SMB、无凭据、每周三）是 **Windows 侧第一次能独立复核卷归属**的来源 ——
`scripts/sa-volume-usage.py` 已经在读它了。

### 23.2 ★★ 同一枚探针：在 NAS 上是判据，在 Windows/SMB 侧是**假阳性机器**

`ENVIRONMENT.md` 把 `stat -c %d` 当同卷判据，开了 **4 处**药。**在 NAS 上它是对的**
（`build-farm.sh` 就这么用）。但从 **Windows/SMB** 侧实测：

```
video 403405124   Download 864492843   homes 2727544675   drive 12209342
web 2153088345    docker 4258917541    docker_ssd 1552128119   qb_temp 1634092467  …
```

**十个共享十个互不相同的号** —— **包括同属 `cachedev_1` 的那六个**。
⇒ 它对**任何一对**都返回「不同」，**分辨力为零**；它给 `docker_ssd ≠ video` 的「正确答案」
**纯属巧合**（它对同卷的 `docker ≠ video` 也这么说）。

**Windows 侧的对照量是 `df`**（按底层文件系统分组，8/8 正确）。

★ **潜伏风险**：`build-farm.sh` 的注释自承**可以从 Windows/SMB 跑** —— 真那么跑，
它的 `stat -c %d` 闸（`:281`）会把**每一个源目录**都判成「与农场不在同一物理卷，跳过」。

**方法（比结论更该带走）**：**先验探针有没有分辨力，再拿它判事。**
办法是拿**已知同类的样本**去撞 —— 本次是拿 `video`/`Download`/`homes`/`drive`/`web`/`docker`
这六个**同卷**的共享去试它，**一撞就露**。

### 23.3 SMB 枚举 ≠ 全量：`net view` / `ls` 都只列 5 个（实际至少 11）

```
net view iSunker-DS423   → 000 临时文件夹nas… / docker_ssd / home / video / 技术文档
ls //iSunker-DS423/     → 同样这 5 个
按 UNC 取得到的           → 上面 5 个 ＋ Download / docker / qb_temp / web /
                           drive / homes / web_packages / ActiveBackupforBusiness
```

**负对照**（否则会以为 MSYS 在瞎猜）：`//iSunker-DS423/nosuchshare_zzz123` →
`No such file or directory` ⇒ MSYS **会**区分真假共享名，所以「`//iSunker-DS423/docker` 能读」
**是真的**。那里面是 `iSunker-DS423_1.hbk`（ABB 的备份）。

⇒ `A.3` 那句「`/volume1/docker` **不是**共享文件夹，SMB 里看不到」**与实测不符**：
它是共享文件夹（DSM 自己的 `share_list.csv` 也这么记），而且 **UNC 直取就能读到**。
准确表述应是「**枚举里看不见**」≠「不是共享文件夹」。

★ 这正是 `ERR-HW-03` 自己的 ★（**看不见 ≠ 不存在**）**在 8 行之外被自己违反**。
★ 另：`net view '\\iSunker-DS423'`（bash 直接传参）报 **1702 绑定句柄无效**，
换 `net view iSunker-DS423` 才通 ⇒ 该探针在本机**不稳**，而 `ERR-HW-03` 的结论正建立在它上面
（「`net view` 没有任何备份共享」）—— **要重核**。

### 23.6 本节的四条方法论

- ★★ **先怀疑探针的分辨力，再拿它判事。** `stat -c %d` 在 NAS 上是对的、文档开了 4 处药，
  可它一到 Windows/SMB 侧就**对任何一对都说「不同」** —— 而那**恰好**让 `docker_ssd ≠ video`
  「说对了」。**验法是拿已知同类的样本去撞它**，不是看它结论对不对。
- ★ **「枚举里看不见」永远不能写成「不存在」。** 同一条知识文档里有（`ERR-HW-03` 的 ★），
  可它在 8 行之外就被违反了 —— **写下来的规矩不会自动执行，每次用那枚探针时都要重念一遍**。
- ★ **别把「不可达的权威源」当成唯一源。** `all_shares` 只在 NAS 上读得到，于是「卷归属」
  这件事在 Windows 侧**长期没有读数**；而一条本来就存在、走 SMB、无凭据的 `share_list.csv`
  就够。**遇到「只能靠 X」时，先问一句 X 是不是真的唯一。**
- ★ **审方案（别人的，或自己上一轮的）时，先逐个符号去代码里对。** 本次方案的机制名**全对**
  （`movie` / `stage` / `SEEDING` / `report_daily` / `.daily-report.state` / `_resolve_searchee_to_pack`
  一个不假），**错的都在"想当然"那一层**：把 dict 说成列、把回灌前的时刻说成回灌后、
  把一个趋势数当成每包数 —— **名字能对上，不等于语义对得上**。

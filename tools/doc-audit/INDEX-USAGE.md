**建于 2026-09-13**（`tools/doc-audit/`）。观察日程：**09-13 建 → 09-20 复跑比对 → 09-27 判据决策**。

> ★ 这份文档**不是第三份事实源**。
> 它只说两件事：**这些投影怎么用**，以及**某一天量到的读数是多少**。
> 环境事实仍然只在 `README` / `SUMMARY` / `ENVIRONMENT` 三处维护；

## 一、这是什么

三份大文档（`README` / `SUMMARY` / `ENVIRONMENT`）是**唯一事实源**。它们太大，检索靠人眼。
`tools/doc-audit/` 干的事不是拆文档，是**给它们做投影**：

```
        ┌─ 事实源（唯一）──────────────────────────┐
        │  README.md   SUMMARY.md   ENVIRONMENT.md │
        └───────────────────┬──────────────────────┘
                            │  只读，可反复跑
        ┌───────────────────┴──────────────────────┐
        │  01_headings  → out/headings.tsv   结构树 │
        │  02_refs      → out/refs.tsv       引用表 │
        │  03_terms     → out/terms.tsv      倒排表 │
        │  04_probes    → out/probes.tsv     事实表 │
        └──────────────────────────────────────────┘
```

**投影只读事实源，事实源不读投影。** 这条方向不能反过来 —— 一旦反了就成了环，两边都会漂。

`out/` 与 `out.baseline-*/` 都在 `.gitignore` 里，但**理由不同**：
`out/` 是**可反复生成的派生数据**，冻进仓库只会变成一条会漂的"事实"；
`out.baseline-*/` 是**一次测量的快照**，进 git 就会从"某天的读数"升级成"事实源"。
两种都不该进 —— **除非 09-20 决定要长期保留那份基线**（那时才另说）。

### `02_refs.py` 管的六族锚点

改标题之前先知道哪些东西挂在标题上：

| 族 | 形态 | 目标在哪 |
|---|---|---|
| ① | `§N` / `§N.M` / `§N.M.K` | SUMMARY 的编号标题（`## 19.` / `### 19.1` / `## §20.8` 都认） |
| ② | `ERR-XX-NN` | `ENVIRONMENT.md` 的 H3 条目 |
| ③ | `README「…」` / `ENVIRONMENT「…」` | 对应文档的标题（**子串命中且必须唯一**） |
| ④ | `A.N` / `B.N` | `ENVIRONMENT.md` 自己的 H2 |
| ⑤ | `弯路 #N` → **LEGACY** | `走过的弯路.md` 已拆（`373b1ea`）⇒ **不可能命中标题**，靠 `ENVIRONMENT.md` 顶部那条反查 grep 解析。**故意不计进悬空**，否则 20 条真引用会被 20 条假警报淹掉 |
| ⑥ | 围栏内的引用 | **不算** —— 代码示例里的 `§N` 是示例，不是引用 |

### ★ 为什么跑围栏要按 CommonMark，不能"见到 ``` 就翻"

`SUMMARY.md` 的 **L5478** 曾经是 `**已沉淀成工具**：```` —— 三个反引号在**行尾**。
CommonMark 说这是**内联代码**，而它会把**下一行的裸 ``` 一起吃掉**。

⇒ 「见到 ``` 就翻」的解析器从那一行起**永久错位**，一路把后面 100+ 个真标题当成代码块内容吞掉。
实测：同一个缺陷骗了两套写法（朴素翻转数出 206，第一版"严格围栏"数出 321，**真值是 340**）。

所以走行逻辑抽在 **`mdwalk.py`** 里，四份脚本共用 —— **不做四份会各自漂的拷贝**。
它还会在收尾时**报围栏缺陷**，而不是闷头算错。

| 冻什么 | 回答什么 | 落点 |
|---|---|---|

| **`out/*.tsv` 的快照副本** | 变了**什么** | `out.baseline-20260913/` |

**第三条是关键：`out/` 是覆盖式写入 —— 09-20 一跑，09-13 那份就没了。**
没有快照，09-20 看到 `02_refs` 报「半悬空 3 条」，你只知道**多了 3 条**、
**不知道是哪 3 条** —— 因为参照系已经被覆盖掉了。

#### ⚠★ hash 变了 **≠** 结构变了 —— 四份表里**三份都嵌了行号**

| 表 | 列 |
|---|---|
| `headings.tsv` | file / level / **line** / slug / title / parent |
| `refs.tsv` | src / **line** / ref / status / target / hint |
| `terms.tsv` | term / file / **line** / context |
| `probes.tsv` | probe / actual / error（**不嵌行号**，但读数**随时间**变） |

⇒ **任何插入 —— 哪怕只加一行正文、标题与关键词一个都没动 —— 都会让前三份的 hash 同时变。**

**09-13 实测**（不是推断）：给 `ENVIRONMENT.md` 加了一行表格 + 一段注，
`headings` / `refs` / `terms` **三份 hash 一起变了**。逐条比对后确认：
**标题序列 `(级别, 文本)` 160 条完全相同；新增的 7 行里 0 个关键词** ——
差异**只在行号列**。

**所以比对必须分两层：**

```bash
cd tools/doc-audit

# 第 1 层（粗筛）：是不是同一份？变了就往下走，**别急着下结论**
sha256sum -c out.baseline-20260913/SHA256SUMS

# 第 2 层（真判据）：**剔掉行号列**再比内容
diff <(cut -f1,2,4,5,6 out.baseline-20260913/headings.tsv) <(cut -f1,2,4,5,6 out/headings.tsv)
diff <(cut -f1,3,4,5,6 out.baseline-20260913/refs.tsv)    <(cut -f1,3,4,5,6 out/refs.tsv)
diff <(cut -f1,2,4    out.baseline-20260913/terms.tsv)    <(cut -f1,2,4    out/terms.tsv)

# 想连"挪到哪了"一起看：直接
diff -r out.baseline-20260913/ out/
```

★ **第 2 层才是"变了没"的真判据** —— 第 1 层只能说「被重跑过 / 上游动过」。
这条与下面 `probes.tsv` 那条**同源**：**一个必然会动的量，不能单独当判据。**

> ⚠ **`probes.tsv` 的 hash 每次跑都会变** —— `retry_after` 在倒数、卷水位在动、
> 批次会写 `timestamp`。所以它的 hash **不能当"变了没"的判据**：
> 拿一个每天都在动的量去判"变没变"，答案永远是"变了"，**等于没判**
> —— 这就是「**判据本身要先被验证一次**」（见 `SUMMARY` §18.10.1）。

★ **冻结之前**该先问什么、冻完**之后**怎么自检 ⇒ 见 **第七节「审计过程自己的坑」**。

**`probes.tsv` 四列要分开判 —— 它们不是一回事：**

| 列 | 09-20 比对时 | 为什么 |
|---|---|---|
| **1、2**（`id` / `name`） | **必须相同** | 变了 = **站没了 / 加了**，是真信号 |
| **3**（`status`） | ★ **不该单独看** | 残留标签 —— `RATE_LIMITED` 在「真在退避」与「窗口早已过去」两种情况下**长得一模一样** |
| **4**（「退避中，剩 N 分钟」/「限流窗口已过」） | **允许变，但要能解释** | 这列是**结论**，不是**读数** |

第 4 列的两个方向要**分开看**：

- 「剩 N 分钟」→「限流窗口已过」= **时间流逝，正常**；
- 「限流窗口已过」→「剩 N 分钟」= ★ **真的又被退避了，要报**。

⇒ 所以第 4 列**不能当"变了就是变了"**，它变了要判**合理不合理**。

## 五、已知的硬限制（别指望它做这些）

| 限制 | 说明 |
|---|---|
| **看不见"层次感"以外的东西** | `01` 只判层级跳跃，判不出「这一节放错了文档」。职责审计要人过 |

## 六、安全纪律（改这些脚本时**必须守住**）

**两条都要有，缺一条就是漏洞：**

1. **不选可能含凭据的列。**
   `cross-seed.db` 的 `indexer.url` **每条都带 `apikey=<Prowlarr 应用级 key>`**，
   那个 key 能开 Prowlarr 上**所有 PT 站**。判「哪个站、什么状态」靠 `id` / `name` / `status` 就够，
   `url` 对判读**零价值**。**能不取就不取** —— 这是主防线。

2. **出口统一过 `redact()`。**
   万一某个探针必须碰这类列，或异常信息里带出来，在**打印和落盘之前**按**值的形状**抹掉。
   按**键名**匹配会漏掉嵌在 `options` / `fields` / 异常文本里的凭据 ⇒ 兜底要按形状。

> 判据是「**只读 + 不回显凭据 + 只打聚合**」这三条同时成立 ——
> 与 `check-deploy-drift.py` 里 `qb-census` / `linkguard` 那两条**同一个形状**。
> 不是「它碰没碰凭据」—— 后者会把所有有用的诊断工具都挡在门外。

另外：**探针一律只读**。库用 `query_only`，UNC 直读、**不 `cp` 副本**（WAL 里未 checkpoint 的数据会丢）。

**它为什么比「hash 每跑必变」更危险**：
基线一旦冻错，**两周后所有比对都是在错的参照系上做的，而比对结果看起来完全正常** ——
「变了 3 处」的真实含义可能是「**基线错了一处 + 今天正常变了两处**」，

### ★ 自检：冻结**后**再跑一次，两次 `sha256` 必须相同

冻完**立刻**再跑一遍投影，比对两次的 hash：

```bash
cd tools/doc-audit

# 三份"确定性投影"：必须逐字节相同
sha256sum out/headings.tsv out/refs.tsv out/terms.tsv
grep -E 'out/(headings|refs|terms)\.tsv' out.baseline-*/SHA256SUMS
```

**相同 ⇒「落定」了。不同 ⇒ 还有东西在改文档**（或哪个脚本有不确定输出）——
**先查清再冻**，别把"没落定"冻成基线。

> ⚠ **`probes.tsv` 必须排除在这条自检之外** —— 它天然每次都不同
> （`retry_after` 在倒数、卷水位在动、批次会写 `timestamp`）。
> 对它用不了"两次相同"，只能用第三节那张**四列表**去判。
> ★ 这一步排除是**必须**的：不排除，这条自检就**每次都报警** ——
> 而「**一个会误报的哨兵，两次之后就没人看了**」。

> **09-13 实测**：写完本节后立刻重跑三份，`headings` / `refs` / `terms` 的 hash
> 与冻结基线**逐个相同** ⇒ **落定**。
> 顺带验掉一件不该靠"应该"的事：**编辑 `tools/` 下的 md 不会动投影** ——
> 因为 `DOCS` 只扫仓库根（第三节那条硬限制）。这条以前只是"推理应该如此"，
> 现在是**实测**。

### ★ hash 变了 **≠** 结构变了（四份表里三份**都嵌行号**）

**发生过的**：09-13 给 `ENVIRONMENT.md` 加了一行表格 + 一段注
（**不新增任何标题、不含任何关键词**），`headings` / `refs` / `terms`
**三份 hash 一起变了** —— 第一反应是"结构被改了"。
**逐条比对后才知道**：标题序列 `(级别, 文本)` **160 条完全相同**、
新增的 7 行里 **0 个关键词**，差异**只在行号列**。

**根因**：`headings.tsv` / `refs.tsv` / `terms.tsv` **都有一列是行号**
⇒ **任何插入都会让它们的 hash 变**，跟"结构变没变"没有关系。

**它属于哪一族**：与 `probes.tsv`「hash 每跑必变」**同源** ——
**一个必然会动的量，不能单独当判据。**
（区别只是：`probes.tsv` 因为**时间**变，这三份因为**编辑**变。）

**动作**：hash **只当粗筛**（它答的是"是不是同一份"）；
**真判据是剔掉行号列再 diff**（第三节那两层比对）。

### ★ 空转的提交/推送：一个「返回 1 被我丢了」，一个「返回 0 骗了我」

**发生过的**：09-13 漏了 `git add` 就 `git commit` —— 那次提交是**空转**，什么都没提交；
紧接着的 `git push` 打印 `Everything up-to-date`，**看起来正像"已经推了"**。

**两条命令的返回值不一样，必须分开说**（09-13 实测，不是推断）：

| 命令 | 空转时返回 | 输出 | 谁在骗人 |
|---|---|---|---|
| `git commit`（暂存区空） | **1** | `nothing to commit, working tree clean` | **没骗人** —— 是我**没接 `&&`、也没读它**，把判决丢了 |
| `git push`（已在最新） | **0** | `Everything up-to-date` | ★ **真的会骗人** —— 0 是"成功"，事实是**什么都没推** |

**它属于哪一族**：与 `SUMMARY` §18.17.3「**绿了但规则没参与**」同源 ——
动作发生了、看起来成功了，但**那件事本身没发生**。

**两条护栏**：

```bash
# ① commit 前：暂存区为空就别 commit（实测：空时 rc=0 ⇒ 护栏成立）
git diff --cached --quiet && { echo "★ 暂存区为空，别 commit"; exit 1; }

# ② push 后：读回真实状态，别信返回值 —— HEAD 与 origin/main 的 hash 骗不了
git rev-parse HEAD origin/main   # 两个 hash 必须相等
```

★ **第二条是关键**：`commit` 的失败还能靠 `&&` 串出来，
**`push` 的失败串不出来 —— 它返回 0**。所以推完必须**读一次真实状态**
（就是 `A.10` 那条 ★：**别信调用的返回值，读回真实状态**）。
